# 🎭 剧团排练台词管理

面向剧团的排练台词网页应用：导演按**场次 / 角色 / 顺序**维护台词，演员登录后只能看到自己获分配角色的排练稿；剧本以**不可改写的发布版本**管理，修改走“修订 → 发布”流程，发布时逐条核对冲突；排练固定引用版本，演员逐场确认，换版与改派会按规则使确认失效。

技术栈：**Node.js 20 + Express + better-sqlite3**，前端为原生 HTML/CSS/JS，无构建步骤。

## 一键启动（Docker Compose，推荐）

```bash
docker compose up -d --build
```

首次启动会自动创建 SQLite 数据库（含表结构和演示数据）。

访问地址： <http://localhost:3000>

停止：

```bash
docker compose down          # 保留数据
docker compose down -v       # 同时删除数据库卷
```

## 本地直接运行（需 Node.js ≥ 20）

```bash
npm install
npm run init-db              # 初始化数据库 + 演示数据（幂等，可重复执行）
npm start
```

访问地址： <http://localhost:3000>

## 核心业务规则

### 版本（不可改写）

- 台词按 `场次 → 顺序 → 角色 → 文本` 组织，每条台词拥有**跨版本稳定 ID**。
- 第一个版本由导演一次性录入；此后**不能直接改动任何已发布版本或其台词**（数据库触发器层面禁止 `UPDATE/DELETE`，绕过接口也会被拒绝）。
- 之后所有修改都必须基于某个已发布版本创建**修订**。

### 修订与发布（冲突逐条核对）

- 创建修订时必须选定一个**基准已发布版本**；每条改动必须标明**被改台词（原文）**与**新文**，原文在提交时从基准版本快照保存。
- 发布时可勾选多个修订：
  1. 逐条拿条目的“原文”与**现行（最新）文本**核对：原文已变化 → 报冲突；修订本身基于旧版本不影响这一判断；
  2. 同一批次多个修订修改同一条台词 → 报冲突；
  3. **只要存在一条冲突，本次发布整体不生效**（不产生新版本，修订保持开放），页面与发布记录中展示每处冲突的原因、条目原文与现行文本；
  4. 全部不冲突时，将现行版本复制为新版本并套用改动，多个互不冲突的修订（即使基准版本不同）合入同一新版本，修订冻结为“已合入”。
- 每次发布尝试（成功 / 冲突）都有留痕，可在“修订与发布”页查看冲突详情。

### 排练与确认

- 创建排练时**固定引用**一个版本；排练稿始终展示该版本内容。要换版本必须点击“**显式换版**”。
- 演员对自己所分配的角色**按场次确认**（只需确认该角色有台词的场次）。
- **换版**时比对两个版本的台词：仅**台词内容发生变化**的角色需要重新确认（其确认记录被清除），未变化角色的确认继续有效。
- **角色改派**给其他演员（或取消分配）后，原演员对该角色的全部确认立即失效，不再计入。
- 导演端排练页实时显示**各排练的待确认演员与待确认场次**；全部确认完毕会有明确标识。

### 权限与拒绝

- 导演端全部接口需要导演会话，演员调用返回 **403 越权访问**。
- 演员只能看到自己获分配角色的排练与台词；访问未参与的排练稿或替别人的角色确认，返回 **403**。
- 引用不存在的版本 / 台词 / 排练，返回 **404 无效版本** 类明确错误；冲突、改写不可变数据等返回 **409**。
- 密码使用 scrypt 加盐哈希，会话存于服务端 SQLite（HttpOnly Cookie）。
